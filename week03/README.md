# Week 03 · AWS Academy S3 실습 가이드

클라우드인프라관리 수업의 Amazon S3 실습 자료입니다. 카페 정적 웹 사이트를 배포하고, 버전 관리·수명 주기·크로스 리전 복제를 설정합니다.

> 이 문서는 제공된 AWS Academy 실습의 **태스크 2~7**을 정리한 안내서입니다. 확인 결과는 직접 실습하며 기록하세요. 콘솔 언어와 업데이트에 따라 메뉴 이름이나 위치가 조금 다를 수 있습니다.

## 학습 목표

- S3 버킷으로 정적 웹 사이트를 호스팅한다.
- 버킷 정책으로 웹 사이트 객체의 퍼블릭 읽기를 허용한다.
- 버전 관리로 수정 전후의 파일을 확인한다.
- 이전 버전의 전환 및 삭제를 수명 주기 규칙으로 설정한다.
- 다른 리전으로 새 객체 버전을 복제하고 삭제 동작을 비교한다.

## 실습 준비와 설정값

AWS Academy 실습을 시작한 뒤 AWS 콘솔에 접속하고, 실습에서 제공하는 웹 사이트 파일을 준비합니다.

| 항목 | 예시 / 설정값 |
| --- | --- |
| 소스 버킷 | `cafe-website-cho` |
| 소스 리전 | 실습에서 지정한 리전 |
| 대상 버킷 | `cafe-backup-cho2` |
| 대상 리전 | 소스와 다른 리전, 예: 미국 서부(오레곤) `us-west-2` |
| 인덱스 문서 | `index.html` |
| 이전 버전 전환 규칙 | `MoveOldVersionsToStandardIA` |
| 이전 버전 삭제 규칙 | `DeleteOldVersions` |
| 복제 규칙 | `CafeReplication` |
| 복제용 IAM 역할 | 실습에서 제공하는 `CafeRole` |

버킷 이름은 예시입니다. 생성 화면에서 사용 가능한 본인만의 이름을 사용하고, 버킷 정책의 ARN도 실제 소스 버킷 이름으로 바꿉니다.

## 태스크 2 · 버킷 생성과 정적 웹 사이트 호스팅

### 1. 소스 버킷 생성

1. **S3 → Buckets(버킷) → 버킷 만들기**로 이동합니다.
2. 버킷 이름을 입력합니다. 예: `cafe-website-cho`
3. **객체 소유권(Object Ownership)**에서 **ACL 활성화됨(ACLs enabled)**을 선택합니다.
4. **퍼블릭 액세스 차단**의 네 가지 항목을 모두 해제합니다.
5. 퍼블릭 액세스 관련 확인란이 표시되면 실습 설정을 확인하고 체크합니다.
6. 화면 아래의 **버킷 만들기**를 선택합니다.

### 2. 정적 웹 사이트 호스팅 활성화

1. **S3 → Buckets → 소스 버킷 → 속성(Properties)**으로 이동합니다.
2. **정적 웹 사이트 호스팅 → 편집**을 선택합니다.
3. 호스팅을 **활성화**하고 정적 웹 사이트 호스팅 유형을 선택합니다.
4. **인덱스 문서**에 `index.html`을 입력하고 **변경 사항 저장**을 선택합니다.
5. 생성된 **버킷 웹 사이트 엔드포인트**를 확인하고 기록합니다.

**확인할 결과:** 정적 웹 사이트 호스팅이 활성화되고 엔드포인트가 표시됩니다. 실제 파일 업로드와 읽기 권한 설정은 다음 태스크에서 진행합니다.

> ACL 활성화는 제공된 실습 절차를 따르는 설정입니다. 버킷 정책을 통한 퍼블릭 읽기는 ACL 활성화 자체만으로 부여되지 않습니다. 웹 사이트 접근에는 객체 읽기 권한과 퍼블릭 액세스 차단 설정이 함께 영향을 줍니다. [AWS 공식 문서: 웹 사이트 접근 권한](https://docs.aws.amazon.com/AmazonS3/latest/userguide/WebsiteAccessPermissionsReqd.html)

## 태스크 3 · 웹 사이트 파일 업로드와 초기 접근 확인

1. **S3 → Buckets → 소스 버킷 → 객체(Objects) → 업로드**로 이동합니다.
2. 실습에서 제공한 웹 사이트 파일을 업로드합니다.
   - `index.html`이 버킷 최상위에 위치하도록 합니다.
   - 이미지·스타일 파일 등은 HTML에서 참조하는 폴더 구조를 유지합니다.
3. 새 웹 브라우저 탭에서 태스크 2의 **버킷 웹 사이트 엔드포인트**를 엽니다.
4. 현재 접근 결과를 확인합니다.
5. AWS Academy 실습 화면에서 **AWS Details → Access the multiple choice questions**를 열고 **질문 1**에 답합니다.

**확인할 결과:** 업로드한 객체가 버킷에 표시됩니다. 아직 퍼블릭 읽기 권한을 부여하지 않았다면 웹 사이트에서 `403 Access Denied`가 나타날 수 있습니다. [AWS 공식 문서: 웹 사이트 응답과 권한](https://docs.aws.amazon.com/AmazonS3/latest/userguide/WebsiteAccessPermissionsReqd.html)

질문 1의 정확한 문항과 선택지는 제공되지 않았으므로, 실습 화면의 질문과 직접 확인한 접근 결과를 기준으로 답합니다.

## 태스크 4 · 버킷 정책으로 퍼블릭 읽기 허용

### 1. 버킷 정책 작성

1. **소스 버킷 → 권한(Permissions) → 버킷 정책 → 편집**으로 이동합니다.
2. [AWS Policy Generator](https://awspolicygen.s3.amazonaws.com/policygen.html)를 이용하거나 아래 정책을 입력합니다.
3. `Resource`의 `cafe-website-cho`를 **본인의 소스 버킷 이름**으로 변경합니다.
4. **변경 사항 저장**을 선택합니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "Statement1",
      "Effect": "Allow",
      "Principal": "*",
      "Action": [
        "s3:GetObject"
      ],
      "Resource": "arn:aws:s3:::cafe-website-cho/*"
    }
  ]
}
```

| 항목 | 의미 |
| --- | --- |
| `Effect: Allow` | 지정한 작업을 허용 |
| `Principal: "*"` | 익명 사용자를 포함한 모든 사용자에게 적용 |
| `Action: s3:GetObject` | 객체 읽기 허용 |
| `Resource: arn:aws:s3:::버킷이름/*` | 해당 버킷 안의 모든 객체에 적용 |

이 정책은 객체 읽기를 허용하며 업로드·삭제 권한은 부여하지 않습니다. 마지막 `/*`를 포함해야 객체를 대상으로 지정할 수 있습니다.

### 2. 웹 사이트 접근 확인

1. 웹 사이트 엔드포인트가 열린 브라우저 탭을 새로고침합니다.
2. 카페의 웹 사이트가 퍼블릭으로 열리는지 확인합니다.

**확인할 결과:** 카페 페이지가 정상적으로 표시됩니다.

접근이 계속 차단된다면 실제 버킷 이름과 정책의 ARN, `index.html`의 위치, 퍼블릭 액세스 차단 설정을 확인합니다. 계정 수준에서 차단하면 버킷 수준에서 해제해도 접근이 차단될 수 있습니다. [AWS 공식 문서: 웹 사이트 접근 권한](https://docs.aws.amazon.com/AmazonS3/latest/userguide/WebsiteAccessPermissionsReqd.html)

## 태스크 5 · 버전 관리와 파일 변경 확인

### 1. 버킷 버전 관리 활성화

1. **소스 버킷 → 속성 → 버킷 버전 관리 → 편집**으로 이동합니다.
2. **활성화 → 변경 사항 저장**을 선택합니다.

### 2. 새 버전 업로드

1. 로컬의 `index.html`을 수정하고 저장합니다.
2. 소스 버킷의 **같은 경로와 같은 파일명**으로 다시 업로드합니다.
3. 웹 사이트를 새로고침하여 변경 사항을 확인합니다.
4. 소스 버킷의 **객체 → 버전 표시(Show versions)**를 켭니다.
5. `index.html`의 최신 버전과 이전 버전, **총 두 버전**을 확인합니다.

위 버전 수는 최초 업로드 후 한 번만 수정해 업로드한 경우의 기준입니다.

### 3. 퀴즈 · 보존된 버전의 실수에 의한 영구 삭제 보호

| 선택지 | 정답 여부 | 설명 |
| --- | --- | --- |
| Cross-Region Replication | ❌ | 다른 리전으로 데이터를 복제하여 재해 복구(DR)에 활용하는 기능 |
| Multi-factor authentication | ✅ | 추가 인증으로 객체 버전의 영구 삭제를 보호하는 기능 |
| CORS | ❌ | 다른 출처(origin)의 웹 애플리케이션에서 보내는 교차 출처 요청을 제어 |
| Bucket policy | ❌ | S3 리소스에 대한 접근 권한을 정의 |

여기서 다중 요소 인증은 구체적으로 **S3 MFA Delete** 개념을 가리킵니다. 로그인 MFA만 설정한다고 객체 버전의 영구 삭제가 자동으로 보호되는 것은 아닙니다. MFA Delete는 객체 버전 영구 삭제와 버전 관리 상태 변경에 추가 인증을 요구합니다.

이 단계는 개념 문항입니다. MFA Delete를 실제로 활성화하는 단계는 포함하지 않습니다. AWS 콘솔에서는 이를 활성화할 수 없으며, 수명 주기 설정과 함께 사용할 수 없습니다. [AWS 공식 문서: MFA Delete](https://docs.aws.amazon.com/AmazonS3/latest/userguide/MultiFactorAuthenticationDelete.html)

## 태스크 6 · 수명 주기 정책 설정

**소스 버킷 → 관리(Management) → 수명 주기 규칙 → 수명 주기 규칙 생성**에서 두 개의 규칙을 만듭니다.

### 1. 이전 버전을 30일 후 S3 Standard-IA로 전환

| 설정 항목 | 입력 / 선택 |
| --- | --- |
| 규칙 이름 | `MoveOldVersionsToStandardIA` |
| 적용 범위 | 버킷의 모든 객체에 적용 |
| 범위 확인 | 이 규칙이 버킷의 모든 객체에 적용된다는 데 동의 |
| 규칙 작업 | 스토리지 클래스 간에 객체의 이전 버전 전환 |
| 비용 확인 | 요청당 전환 비용이 발생함을 인지한다는 확인란 체크(표시되는 경우) |
| 대상 스토리지 클래스 | Standard-IA |
| 객체가 최신 버전이 아니게 된 후 경과 일수 | `30` |

설정을 확인하고 **규칙 생성**을 선택합니다. 보존할 최신 이전 버전 수 등 추가 조건은 이 실습에서 별도로 지정하지 않습니다.

**30일의 기준은 최초 업로드 날짜가 아니라, 해당 버전이 이전 버전(Noncurrent)이 된 시점입니다.**

예를 들어 V1을 업로드한 뒤 나중에 V2를 같은 키로 업로드하면 V1이 이전 버전이 됩니다. V1의 전환 기간은 **V2가 생성되어 V1이 이전 버전이 된 때부터** 계산합니다. [AWS 공식 문서: 수명 주기 규칙과 이전 버전](https://docs.aws.amazon.com/AmazonS3/latest/userguide/intro-lifecycle-rules.html)

### 2. 이전 버전을 365일 후 영구 삭제

1. 다시 **수명 주기 규칙 생성**을 선택합니다.
2. 아래와 같이 설정한 뒤 **규칙 생성**을 선택합니다.

| 설정 항목 | 입력 / 선택 |
| --- | --- |
| 규칙 이름 | `DeleteOldVersions` |
| 적용 범위 | 버킷의 모든 객체에 적용 |
| 범위 확인 | 이 규칙이 버킷의 모든 객체에 적용된다는 데 동의 |
| 규칙 작업 | 객체의 이전 버전 영구 삭제 |
| 객체가 최신이 아닌 상태로 전환된 후 경과 일수 | `365` |

365일도 **이전 버전이 된 시점**을 기준으로 계산합니다. Standard-IA로 전환한 시점부터 365일을 추가하는 것이 아닙니다. 이 작업은 이전 버전을 영구 삭제합니다. [AWS 공식 문서: NoncurrentVersionExpiration](https://docs.aws.amazon.com/AmazonS3/latest/userguide/intro-lifecycle-rules.html)

### 3. 규칙 확인과 실제 적용 조건

| 이전 버전이 된 후 경과 기간 | 설정한 동작 |
| --- | --- |
| 30일 | 조건을 충족한 이전 버전을 Standard-IA로 전환 |
| 365일 | 조건을 충족한 이전 버전을 영구 삭제 |

**확인할 결과:** 관리 탭에 두 규칙이 생성되어 활성화되어 있습니다. 실습 중에는 설정을 확인하며, 30일·365일 후의 실행 결과를 즉시 확인하는 것은 아닙니다.

현재 S3의 기본 수명 주기 전환 동작에서는 **128KB 미만의 객체는 전환되지 않습니다.** 작은 `index.html`도 이 제한의 영향을 받을 수 있습니다. 규칙의 기간 설정과 개별 객체의 실제 전환 가능 여부를 구분하세요. [AWS 공식 문서: 전환 조건과 작은 객체 제한](https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-transition-general-considerations.html)

## 태스크 7 · 크로스 리전 복제(CRR) 사용

### 1. 다른 리전에 대상 버킷 생성

1. S3에서 **버킷 만들기**를 선택합니다.
2. **소스와 다른 리전**을 선택합니다. 예: 미국 서부(오레곤), `us-west-2`
3. 대상 버킷 이름을 입력합니다. 예: `cafe-backup-cho2`
4. **버킷 버전 관리**를 활성화합니다.
5. **버킷 만들기**를 선택합니다.

S3 Replication은 객체 버전을 복제하므로 **소스와 대상 버킷 모두 버전 관리가 활성화되어 있어야 합니다.** 복제 작업을 수행할 IAM 권한도 필요합니다. [AWS 공식 문서: 복제 요구 사항](https://docs.aws.amazon.com/AmazonS3/latest/userguide/replication-requirements.html)

### 2. 소스 버킷에 복제 규칙 생성

1. 소스 버킷으로 돌아가 **관리 → 복제 규칙 → 복제 규칙 생성**을 선택합니다.
2. 복제 규칙 이름에 `CafeReplication`을 입력하고 규칙이 활성화되어 있는지 확인합니다.
3. **버킷의 모든 객체에 적용**을 선택합니다.
4. 대상에서 **S3 찾아보기**를 선택합니다.
5. 두 번째 버킷(`cafe-backup-cho2`)을 선택한 뒤 **경로 선택**을 누릅니다.
6. IAM 역할에서 실습에 제공된 **`CafeRole`**을 선택합니다.
7. 별도 창에서 `CafeRole`의 권한 내용을 확인합니다.
8. 이 실습에서는 **삭제 마커 복제(Delete marker replication)를 활성화하지 않은 상태**로 둡니다.
9. **저장**을 선택합니다.
10. **기존 객체를 복제하시겠습니까?**가 표시되면 **아니요. 기존 객체를 복제하지 않습니다.**를 선택하고 **제출**합니다.

### 3. 기존 객체 복제 여부 확인 · 질문 3

1. 대상 버킷의 **객체** 탭을 엽니다.
2. 복제 규칙 생성 전에 소스 버킷에 있던 객체가 표시되지 않는지 확인합니다.
3. 질문 3 **“대상 버킷에 소스 버킷의 객체가 표시됩니까?”**에 **No**를 선택하고 **Submit**합니다.

**이유:** 기존 객체 복제를 선택하지 않았으므로, 규칙 설정 이전의 객체는 이 규칙만으로 소급 복제되지 않습니다. [AWS 공식 문서: 복제되는 항목과 제외되는 항목](https://docs.aws.amazon.com/AmazonS3/latest/userguide/replication-what-is-isnot-replicated.html)

### 4. 새 버전 업로드와 복제 확인

1. 로컬 `index.html`에서 아래 부분을 찾습니다.

   ```html
   <div class="center">Caf&eacute;</div>
   ```

2. 화면에서 구분할 수 있도록 문구를 수정합니다. 예:

   ```html
   <div class="center">Caf&eacute; - CRR Test</div>
   ```

3. 수정한 파일을 소스 버킷의 동일 경로에 `index.html`로 업로드합니다.
4. 소스 버킷에서 **버전 표시(Show versions)**를 켜고 **총 세 버전**을 확인합니다.
5. 대상 버킷으로 이동하여 새 `index.html`이 복제되었는지 확인합니다.

**확인할 결과:** 실습 순서대로 각각 한 번씩 수정했다면 소스에는 세 버전이 있고, 대상에는 복제 규칙 생성 후 업로드한 새 버전이 표시됩니다. 복제는 비동기적으로 처리되므로 바로 보이지 않으면 잠시 후 새로고침합니다. [AWS 공식 문서: 복제 요구 사항과 고려 사항](https://docs.aws.amazon.com/AmazonS3/latest/userguide/replication-requirements.html)

### 5. 소스 객체 삭제와 대상 확인 · 질문 4

1. 새 버전이 대상에 복제된 것을 확인한 뒤 소스 버킷으로 돌아갑니다.
2. 일반 객체 목록에서 `index.html`을 선택해 **삭제**합니다.
3. 대상 버킷에서 복제된 `index.html`이 남아 있는지 확인합니다.
4. 질문 4 **“소스 버킷에서 방금 삭제한 버전이 대상 버킷에서도 삭제되었습니까?”**에 **No**를 선택하고 **Submit**합니다.

**삭제 동작 구분**

- 버전 관리가 활성화된 버킷에서 버전 ID를 지정하지 않고 일반 삭제하면 **삭제 마커(Delete marker)**가 추가됩니다.
- 이 실습처럼 삭제 마커 복제를 활성화하지 않으면 해당 마커가 대상에 복제되지 않아 대상 객체가 유지됩니다.
- 특정 버전 ID를 지정해 소스의 버전을 영구 삭제하더라도, 해당 버전의 삭제 작업은 대상에 복제되지 않습니다.

따라서 질문 4의 No는 이 실습 설정에 따른 답입니다. 삭제 마커 복제를 별도로 활성화한 경우에는 일반 삭제 후 대상에서 보이는 결과가 달라질 수 있습니다. [AWS 공식 문서: 복제와 삭제 동작](https://docs.aws.amazon.com/AmazonS3/latest/userguide/replication-what-is-isnot-replicated.html)
